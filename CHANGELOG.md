# Changelog

## [Unreleased]

### Added

- **Go-to-definition and document links follow custom tags** ([#345](https://github.com/cfmleditor/clif/issues/345)). `<cf_name>` and its end tag, `cf_name()` in cfscript, `<cfmodule name="a.b">`, `<cfmodule template>`, `cfmodule()` and Lucee's `module` statement, `<cfimport taglib prefix>` tags, and tags from a configured tag library prefix go to the template the engine would run: the caller's directory, then `this.customTagPaths` (a list, an array, a struct, or `listAppend` onto it, read through includes and a parent `Application.cfc`), then the new `customTagPaths` config key, then the CFConfig file's `customTagMappings` (Lucee) or `customTagPaths` (CommandBox), searched recursively where an entry says `recursive` or the CFConfig sets `customTagDeepSearch`. A name is matched without case and tried as `.cfm`, `.cfc` and `.cfml`; a built-in tag never goes to a library file. Over the corpus, 630 of RustCFML's 637 `cf_` calls resolve (the rest have no template, or need deep search its tests turn on per run), Lucee's 69 of 74 `cfmodule` templates and 17 of 20 `cfimport` tags (the rest name server mappings), and Mura's 57 of 85 `cf_` calls (the rest are in `core/modules`, under a deny-access `Application.cfc` of their own). Typing a custom tag's `attributes.x` from its callers now reads the calls with the same scanner, without regular expressions, from the text each file was indexed with rather than reading every file again; a call inside a CFML comment no longer counts, and a script `cf_name(…)` or `cfmodule(…)` call is an opaque caller. `unresolved` is byte-identical on RustCFML, Lucee and Mura.
- **A file with old Mac line endings is read line by line.** A bare carriage return ends a line, as the Language Server Protocol and every editor count it, where the parser, its line index and tree-sitter counted line feeds alone: such a file was all line 0, and every position the server gave in it was wrong. The text is made right where it is read (`lex.NormalizeLineBreaks`, which keeps every offset), and formatting edits to such a document keep its carriage returns. On ColdBox's samples, findings that sat on line 1 now carry their lines, and 17 fewer remain.
- **Walkers that find the same things agree.** Measured against the tree-sitter grammar over the corpus (`.ai/docs/SCANNER-CONSOLIDATION.md`):
  - `ParseVars` and `FindFuncScopes` now take function scopes from the parse's own walk. The separate finder they used ended 1,381 `<cffunction>` blocks at the first `<cfscript>` in their body and missed 339 script functions; it is gone, and the scopes now match the parse on all 14,949 files. Go-to-definition placed a variable declared after such a block outside its function.
  - A component's variables are read by one walk, the parse's own. A second scanner found them for completion and the index (`VariablesVars`, `ThisVars`). Judged against the grammar it declared some 3,400 variables that were none: the `b` of every `a.b = x`, a name compared with `==`, and `local.x` outside a function. It also missed 391 the parse finds, such as plain `x = 1;` and `for (x in …)`. The parse in turn stopped reading struct literal keys and named arguments written one per line as declarations, and stopped taking the next line for the value of `x = {}` with no semicolon. RustCFML's scan loses 9 false findings, and token passes fell to 11.8 on ContentBox and 14.1 on Mura.
  - A `.cfm` holding no CF tag is read as text, not script, when its first line could not begin CFScript: an INI `[section]` header, a `#` heading or comment. Mura's `settings.ini.cfm` templates, ContentBox's `runtime.properties.cfm` and cbmarkdown's Markdown view were each one script region, every `key=value` in them a declaration. A RustCFML `#!` script stays script, and go-to-definition's variables now split a file as the parse does.
  - A tag's attributes are read by one scanner with a CF and an HTML mode (`attrScanner`), where five readers each read them their own way. In a CF tag a doubled quote is an escaped one and a `#...#` holds strings of its own; in markup a value ends at its quote. Judged against the grammar, the old readers were wrong on 516 to 1,815 corpus attributes each, losing an attribute after a space before `=`, a name with a digit (`show3d`) and an unquoted value (`default=0`), and finding a name inside another's value. A `<` inside a quoted value (`hint="… <br />"`, `output="</cfif>"`) no longer ends the tag, which lost every attribute after it.
  - Document links are read as the parse splits the file, with the attribute scanner in tag regions and the script scanner in script ones, where a line scan took any `template=`, `href=` or `action=`. A link is no longer offered for an include in a comment, a CF tag's `action="list"`, a `<cfset href = …>`, prose, or a struct key named `template`; `href` links on markup, `action` on a form, and a quoted `template` on a CF tag. `cfinclude(template="x")` in script, a `<cfinclude>` written in a script component and a `cfmodule` template with spaces around `=` are now linked, and a markup tag cut by a `<cfif>` keeps its later `href`. The code map loses only include edges that were in comments or struct keys.
  - Includes are read by the same walk, its include kind. The include scan looked for the word `include` anywhere and skipped `<!--- --->` comments alone, so a `//` or `/* */` comment, a string, and a call through another object such as Wheels' `application.wo.$include(…)` each made an include the code map did not have; over the corpus 20 such go. A function that includes the template an argument names, such as Wheels' `$include(template)`, makes each unqualified call of it in the same file an include, as the old scan did for that one by accident and now does for any. `unresolved` is byte-identical on eight corpora. The `<cfdirectory>` listing an include follows is read with the attribute scanner, and the startup reader's constructor includes come from the same scan.
  - The application-section, producer-plan and Wheels method finders read a string as the parse does. A `#...#` holding a quoted `"{"`, as in ColdBox's `Router.cfc`, made each count a brace that was not there, and lose every function after it: 417, 459 and 1,208 functions across the corpus, now 61, 60 and 136, mostly closures they do not count by design.
  - Every resolver walk reads a string as the parse does. 30 scanners over a file, a function body or an expression, the resolver's shared token memo among them, read CFScript's `"#f("x")#"` as two strings; `parser.NewSourceScanner` applies CFScript's rule to script text and to a tag file's `<cfscript>` blocks, and markup's rule to the rest. 854 corpus files tokenise differently; `unresolved` is byte-identical on eight corpora, with no measurable change in time.
  - A `<!--- --->` comment is skipped by one reader, written to the grammar's rule: comments nest, and open and close with three or more dashes. The scanner closed one at `-->`, and the reaching-refs and producer-plan tag walks at the first `--->`, so a tag after a nested comment's inner close, which 19 corpus files have, was read as live code. `unresolved` is byte-identical on eight corpora.
  - A Wheels include wrapper is proven by the fact the include scan reads (`parser.IncludeWrappers`), as well as by newer Wheels' pinned bodies: an older `Global.cfc` that includes `#LCase(arguments.template)#` in `$include` itself now types the templates `application.wo.$include(…)` runs, as a newer one did.
  - The Application.cfc mapping walk reads its includes with `IncludeSites`, so an include in a page's prose or an HTML comment no longer runs as part of the constructor.
  - Byte classes that several packages each defined identically (regexp `\s`, quote, word start, identifier, `\w`, ASCII letter and ASCII lowering) live once in `internal/lex`, each tested over all 256 bytes against every copy it replaced.
  - Every line table is one `parser.LineTable`, where five were written by hand, each checked against the copy it replaced; the resolver's cached tables take half the memory, and four lookups that counted lines from the top of a file once per site read the table instead.
  - The resolver reads `<cfloop>`, `<cfargument>`, `<cffunction>`, `<cfreturn>` and shared-scope `<cfset>` tags with the parse's tag walk (`parser.CFTags`), not regular expressions: a commented-out tag is none, and a `>` inside a quoted value no longer ends a tag.
  - The resolver reads framework calls (setView/renderView, announce, hasMany, `map().to()`, `super.init()`, applicationHelper, `dspObject_include`, Lucee's registry recipe and others) from code tokens instead of regular expressions, so a commented-out or quoted call no longer counts as one.
  - The resolver's 29 single-expression regular expressions are byte readers, each held to its original expression by a differential and a fuzz test.
  - The resolver's function finders (Wheels methods, producer plans, tag bodies, handler actions, Application.cfc sections and others) read the functions the parse found (`ParseResult.FunctionSpans`), so a function in a comment or a page's JavaScript is no longer taken for one; the parse in turn now reads `string[]` returns, modifiers either side of the access, `component function`, colon attributes and a self-closing `<cffunction>`.
  - The resolver's per-name write and guard checks (an rc or prc assignment, a variable a template reads, a lazy field, an init argument's store, structKeyExists/isDefined/isNull/isInstanceOf guards) read the code's tokens, so a write or guard in a comment or a string no longer counts.
  - The resolver's remaining readers of CFML bodies (script returns, Lucee script loops, lazy getters, Preside service headers and local declarations) read the parse's tokens and tags, so commented-out code and text inside strings no longer count.
  - The parser's older entry points (`ParseFunctionDefs`, `ParseComponentRefs`, `ParseVars`, `FindFuncScopes`, `FunctionSpansOf`, `AllVars`) read one shallow `ParseWithOptions` through the new `KeepVars` and `ScopesOnly` options, so a `<cfscript>` island inside a `<cffunction>` is read as part of that function everywhere.
  - The framework call readers (view renders, announcements, FW/1, Mura display objects, Wheels associations, WireBox maps, cborm entities, includeUDF, Lucee registries) take their calls from the parse (`ParseOptions.FindCalls`), so a function's own declaration is no longer read as a call of it.
  - The resolver's write readers (`setsName`, FW/1 rc and ColdBox prc hand-offs, lazy getters, subclass literals, init arguments, public properties) read the assignments the parse records (`ParseOptions.RecordAssignments`) instead of walking tokens per name, so tag attributes, named arguments, struct keys, markup and SQL no longer count as writes.
  - The reaching-assignment, guarded-call, assignment-continuation and component-attribute readers, and the Application.cfc mapping walk, count braces as the parser does: a brace in a string, a `#…#` argument or a comment no longer opens or closes a block, a body-less method or the word "function" in prose no longer hides the mappings after it, and a `{` in a doc comment no longer loses a component's `delegates`.
- **A batch scan reads each file fewer times.** Measured with counters on the scanner, a scan of Mura tokenised 25.5 times the text it holds and now about 15; ContentBox went from 15.9 to about 13.4. Plain parses that already had a cached twin share it; the startup sources' facts, `applicationScan`, the WireBox module reads, the collection readers and DI/1's managed property metadata are kept by their text; project-assumption walks are kept by file and checked by re-reading what they read; producer plans are built on first use and in one scan; and the shared token memo keeps two generations instead of dropping everything when full, which had made a scan's cost swing by a third between runs. Folding reuses the parse's regions and keeps its spans per document version. `unresolved` is byte-identical on six corpora. See `.ai/docs/PARSE-PASSES-PLAN.md`.
- **The parser reads its remaining fixed text shapes without regular expressions.** `this.beanPaths`, FW/1's `diLocations` and `extends="framework.one"`, `this.mappings["/k"]` terms, `@serviceproperty` annotations, a mock's `className`, the markup-template check, resolver `$N` placeholders and Mura's startup service loops are read by a byte cursor (`internal/parser/text_shapes.go`). Each replaced expression is kept in its test as an oracle, held to agree on 200,000 generated texts and under `FuzzTextShapes`; `unresolved` is byte-identical on six corpora. Only user-written `componentResolvers` patterns and CFML's own `reReplace` still compile a regular expression.

- **`unresolved --verbose` says how many calls each classify rule let through.** The resolved count includes calls accepted for their reason alone (`untypedHop`, `sharedMember`, `distinctiveMember`, …), which are judgements about the receiver and not proofs; nothing listed them. They are now counted by rule name in `Report.Rules` and printed on stderr after the totals. A plain built-in function is not counted. The report on stdout is unchanged.

### Changed

- **A batch scan tokenizes each file once for the resolver's whole-file readers.** The consolidation's token readers each tokenized whole files on their own, and three caches held the same tokens: passes over the text rose from 11.7 to 18.2 on ContentBox and from 14.2 to 20.6 on Mura, and memory by up to 13%, though CPU stayed within 3%. One entry per text now serves every whole-file reader, the word checks in front of them are back, and the include walk skips script that names no include: 16.1 and 17.4 passes, memory within 5–8% of before, and Mura's CPU below it. `unresolved` is byte-identical on eight corpora.

- Go 1.27.4, for a standard-library `net/http` advisory (GO-2026-6859) that failed `govulncheck`; `modernc.org/libc` 1.81.0 and `go-json-experiment/json` v1.27.2.

- **Parse workers no longer queue on one lock to look up a resolver match.** The memo of which component an expression resolves to is shared by every parse worker of a batch run, and every miss took its single write lock: in a tassweb scan workers spent four seconds waiting on it. A shared set's memo is now 64 shards by expression (`resolverMemo`), each with its own lock, a 64th of the cap and 128 bytes to itself (arm64's cache line, two of amd64's); a set built for one parse, which shares its memo with nothing, keeps a single shard and the whole cap. The tassweb scan is about 5% faster in wall time (5.32s against 5.59s) and spends 0.6s less in the kernel, with the same user CPU (three runs each, alternated), and `unresolved` is byte-identical.

- **The caller index holds file numbers, not paths.** Argument inference indexes, for every call-shaped name, the files it appears in, and each entry was a 16-byte copy of the path's string header, so a file was paid for once per name it calls. Each file is now numbered once (`callerIndex.add`) and a name lists 4-byte numbers: 19MB at a tassweb scan's peak against 38MB, with no measurable CPU change. `callerFiles` answers as before, each file once and sorted by path (`TestCallerFilesAreSortedPathsWhateverTheirNumbers`); a name's list is sorted by the first ask for it, outside the index's lock, and kept until a file is added under it; `unresolved` is byte-identical on tassweb and the 47 corpus projects.

- **A call decided by how many components declare its name is decided after the scan.** `sharedMember` (five files), `distinctiveMember` (exactly one), `undeclaredMember` and `knownNativeMember` (none) read a count that includes the framework stubs the scan has reached; a stub is indexed when something first resolves to it, which in a parallel scan is whenever a worker gets there, so the count moved by one or two between runs of the same build and a call switched rules, or switched between built-in and unresolved in the map's stats (ContentBox's unresolved count read 855, 856 or 857; main did it about one run in 30). A call in the receiver-with-no-ref family that one of these rules could still decide is now left open (`ClassifyOptions.DeferCounts`, `resolve.Pending`) and settled once the scan is done: `unresolved` after its workers finish, the code map after its scan and before a file is stored in a cache. 30 map builds and 25 rule tables on ContentBox are identical. What it changes: one Lucee finding goes (`file.toPath` in `WatchService.cfc`, accepted now by `sharedMember`: four workspace components and one framework stub declare `toPath`, five once the stub has been reached, which it had not been when the call used to be classified); the map's built-in count on Masa drops by nine and its unresolved count rises by nine, on ContentBox by one; the other corpora and every graph's nodes and edges are unchanged. Not applied with `--global-defs`, in `explain` or in the editor.

- **`callbackParameterComponent` hands three lookups to functions of their own** (`closureParameter`: the innermost closure around the call and the parameter's position; `callbackProviderFunc`: the function the provider call runs; `callbackParameterName`: the provider's name for the closure it is passed). The path-by-path walk stays in the function. The code moved as it was; breaking the positional-parameter lookup or the closure bounds fails the callback tests, and `unresolved` is byte-identical on all seven corpora.

- **`producerScript.statement` hands `if`, loops and `try` to methods of their own** (`ifStatement`, `loopStatement`, `tryStatement`). The branches of those that run out of input, which no test reached, are pinned: a table reads 24 statement forms, each well-formed and cut short, and checks the node kind, whether the plan failed and what the body and alternative hold (removing the `finally` check fails it). The code moved as it was, and `unresolved` is byte-identical on all seven corpora.

- **`returnComponentOf` hands three of its stages to functions of their own** (`producerReturn`, `sourcesReturn`, `declaredReturn`); the order of the chain (an abstract base's overrides, a declared collection, the plan of the body, the recorded sources, what the function names, the bare type, the doc comment) stays in the function. The code moved as it was; the plan stage says whether it decided with a second result, since an answer of "" can ask for the contracts below it to be skipped. Its branches were covered, and `unresolved` is byte-identical on all seven corpora.

- **`flatParamParts` is a small collector.** The entries so far, the one being read, and the comment it holds back are a `paramCollector`; `add` reads one child of the list and `addOther` the comments and kept text. The code moved as it was. The formatted output of 1,298 files across TestBox, FW/1, ColdBox and Galaxie (the first 400 of each, or all there are) is byte-identical before and after, and `make corpus BASELINE=` over those five projects and ContentBox reports no file changing verdict. One branch (a parameter starting with no comma after the previous one's name) was reached by no test before and still is: it is grammar error recovery, and the move did not touch it.

- **`runServer` hands its two modes to `runDaemon` and `runStandalone`.** The startup (logging, crash reports, cache limits) stays in `runServer`; serving through or as the project's daemon, and serving a standalone session, are functions of their own. The code moved as it was. Checked by driving the old and new binary over stdio in both modes (initialize, shutdown, exit): the same replies and exit status.

- **The MCP server's tool dispatch is a table of handlers.** `run` was a 133-line switch with a case per tool; each tool is now a short method (`searchSymbols`, `findPath`, `explainCall`, …) found by name in `toolHandlers`, and `run` keeps the argument parsing, the no-map refusal and the unknown-tool error. Nothing exercised the switch before beyond three argument checks: every tool is now called through the wire for a good call and for missing arguments, a server without its backing gets the remedy in the message, and a test fails when an advertised tool has no handler (checked by removing one). No change in behaviour.

- **`Map.WriteText` is five sections.** The counts, the detached islands, the hubs, the cycles and the unreferenced list are functions of their own, and the three copies of "the first `limit` of these" are one helper. The text had no test; three outputs (every section, a limit of one, an empty map) were captured from the unchanged code first, and TestBox's text report is unchanged apart from the build time. ContentBox's differs from the old binary's only in the unresolved/builtin split, which moves by one or two between runs of any build (see the code-map guide).

- **`handleDidChange` is three steps.** Applying the changes (`applyChanges`) and bringing the server's views up to date (`afterEdit`) are functions of their own; the handler keeps the guards, the burst path and the deferral. The paths no test reached (an unreadable notification, no changes, a file that is not CFML, a document never opened, a whole-document replacement) have tests, written before the move. No change in behaviour.

- **CLAUDE.md is 331 lines, not 2,855.** The architecture notes moved, unchanged, to nine files under `.ai/docs/guide/` (parser, formatter, code map, structure, LSP, text and includes, resolvers, testing, verification), and CLAUDE.md keeps the commands, the package map, the configuration table, the `explain` workflow and an index saying which file to read for which area. Every non-blank line of the old file is in exactly one new file (checked by comparing the two as multisets); the only additions are the index, a title and a one-line description per file. References to a moved section, in the docs, in comments and in the Configuration table, now name the file that holds it.

- **A Mura template's matching `dspObject_include` calls are found once per path** (`muraSitesFor`). Every untyped name a template reads matched its path against each call's `theFile` pattern again (two passes), 0.6 s of a MasaCMS scan's 9 s of CPU; which calls could include a template depends on its path alone. MasaCMS 2.52 s to 2.44 s (six interleaved runs); the output is byte-identical on all seven corpora.

- **`unresolved` on Lucee is 35% faster** (3.65 s to 2.37 s, five interleaved runs). A base's leaf subclasses (`leafSubclasses`) are cached under `Index.ShapeGeneration`, which moved for every file indexed, and Lucee indexes 435 files while it scans (stubs and the like), so the cache was emptied about 150 times and `testbox/system/BaseSpec.cfc` was walked 476 times at 12 ms. The generation now moves only for a change that a name can reach (`internal/index/shape.go`): a file that extends something, one whose file name or entity name an `extends` in the index spells (that is how a bare name resolves, `FindFilesByBasename` and `NamedEntities`), a `ModuleConfig` or `WireBox` file (read for WireBox ids), anything once a computed `extends` exists, and a re-index that changed what the file extends or declares. A new file that extends nothing and that no extends names, an identical re-index, and recording that an unindexed file extends nothing no longer move it; a name's first mention moves it with its own file, so a file skipped earlier is looked at again. Tests pin every case that must move it (each fails when its check is removed) and the ones that must not, and one end to end: a plain file leaves the cached leaves standing, a later subclass or a plain file that starts extending the base still appears. The output is byte-identical on all seven corpora; nothing else is faster (the other corpora do not use the walk much).

- **`unresolved` on Lucee is about 5% faster** (3.60 s to 3.41 s, six interleaved runs). `ComponentPath`'s memo was a map behind the resolver's `RWMutex`, and every call read it: a read lock is an atomic add on one shared cache line, which was 0.58 s of a 12 s profile spent on four cores waiting for each other. It is a `sync.Map` now, read without a lock; entries are never removed. The output is byte-identical on all seven corpora. `Index.ExtendsForFile` and the URI-key memo show the same cost (0.3 s and 0.14 s) and are not changed.

- **A controller's `setView` calls are read once per text, not once per view looked up** (`fw1SetViews`). `fw1ActionsUncached` ran an expression over every controller's whole text for each view it was asked about, 0.66 s of a MasaCMS scan's 12 s of CPU; the profile no longer shows it. Wall time on Masa is within noise (2.9 s both ways), since the scan has other limits. A test pins the calls it reads (with and without a subsystem, `action =`, and a lookalike); the output is byte-identical on all seven corpora.

- **A source's plain parse is kept, not redone per function** (`sourceInfo.plainParse`). `elementReturn` parsed the whole file again, with no resolver, for every function of it whose return type was looked up: a sixth of a MasaCMS scan. A parse with no options is a function of the text alone, so it is shared and kept with the source (a parse's lazy parts are locked, and the test shares one across eight goroutines under `-race`). With the change above, Masa goes from 4.3 s to 2.6 s (-39%) and Galaxie from 1.28 s to 0.78 s (-39%); ContentBox -22% and ColdBox -12%, FW/1 -37% on a 0.3 s scan, Lucee unchanged. The output is byte-identical on all seven corpora.

- **`unresolved` is up to 21% faster on MasaCMS and 23% on Galaxie** (4.3 s to 3.4 s on Masa; the others 4-15%). Whether a file holds a `return items[ i ]` anywhere was answered for every function of the file whose return type is looked up, by two regular expressions over the whole text: a quarter of Masa's CPU. It is read once per source now (`sourceInfo.holdsElementReturn`, beside the other facts read from content on first use). The output is byte-identical on all seven corpora.

- **A scan of a workspace with thousands of subclasses of one base is 20 times faster.** `unresolved` over Lucee took 110 s and takes 5 s: the walk behind "every leaf subclass of this base" scanned the whole extends map once per component under the base, and compared each file with the list so far by cleaning both paths (98% of the scan). One pass over the map now answers every name (`Index.ExtendersByName`), and the list is a set. The output is byte-identical on Lucee, ContentBox, ColdBox, TestBox and FW/1. Looking up a file's index key (`uriKey`, a decode and a lowercase on every lookup) is remembered, which takes Lucee's scan from 4.1 s to 3.6 s.
- **`unresolved` is up to 22% faster** on component-heavy workspaces (ColdBox 22%, ContentBox 14%): three rules that asked a question of a file's text with a regular expression over the whole file (does it declare a function of this name, does it assign this variable, what is this function's body) now find the name and check around it, and a handful more skip a file that lacks the one word every match needs, or find the name directly. A third batch finds the fixed word each remaining expression starts with and tries the original expression only there (render and view calls, action starts, interceptor announces, the FW/1 view call, `prc.response` writes, `customErrorTemplate`), a further 4–9% on ColdBox and ContentBox. The output is byte-identical on ColdBox, TestBox, FW/1, ContentBox and Lucee.

### Fixed

- **`unresolved` finishes on Preside again.** Parsing a file can ask what one of its own functions returns, and since 0.6.0 some of the answers read that function's body from the file's own parse (`returnsCriteriaList` through `fnBody`, `builtCollectionElement`). The parse was cached only once it finished, so each ask parsed the file again, and the asks multiplied: a 50-line cut of Preside's `PageTypesService.cfc` took ten seconds, and the whole checkout grew to 10GB and overflowed its stack where 0.6.0 took 1.6s. `handlerParse` now gives a goroutine that asks for a file it is already parsing the file's plain parse, as `elementReturn` always has (`handler_reentry.go`), and does not cache a parse that read another file's unfinished one, so what is cached does not depend on which file the scan reached first. Preside takes 1.3s; five runs are identical, and `unresolved` is byte-identical on tassweb and the other 46 corpus projects. `TestAFileAskingAboutItselfIsNotParsedAgainWhileItIsParsed`.

- **A scan costs what 0.6.0 did again.** Four checks added since 0.6.0 redid work on every lookup: the reaching-assignment check read a function's or template's blocks from its start for each use (`scopeBlockEvents` now keeps them per scope) and walked the lines above it for assignments (it reads the file's assignment table, `contentFacts`); `hasSelfDefaultParam` searched the whole file for `"self"` (once per source now); and every scan worker built the included templates' function table at once (`sync.Once`). On tassweb `unresolved` went from 45.6s of CPU to 37.1s (0.6.0: 37.8s), with byte-identical output there and on the corpus. `TestBlockPathsDoesNotRescanTheScope`, `TestScopeBlockEventsMatchAScanOfTheShorterText`.

- **`registeredAssertion` is 27 lines, not 139.** The rule is four checks that each answer found-or-not, in the order it made them: BaseSpec's registrar and the assertion component it builds (`assertionRegistrar`), the selected `beforeTests` and the names it registers (`assertionHook`), the components from the spec up to the registrar (`assertionChainStable`) and the calling method up to the call (`assertionCallStable`). Eighteen cases written first pin where it declines (the calling method and the receiver's spelling, the registrar's argument, visibility and file, where the assertion is built, the hook's existence, arguments, visibility and body, another name registered, a parent's hook, a parent that cannot be found) and two where it accepts; they fail with the hook-visibility check or the BaseSpec file-name check removed. `unresolved` is byte-identical on all seven corpora.

- **`mergeExpressionCalls` is 87 lines, not 139.** Choosing and running the sub-parse of an expression (`expressionSubParse`, one parse that wraps the expression when it holds member assignments), recording the constructions it found (`recordInstantiations`) and matching its calls against those the string paths recorded (`exprKeyOf`) are their own. The function was fully covered by the tag-expression and interpolation tests; `gapcheck` and the parser tests pass, the allocation budget holds and `unresolved` is byte-identical on all seven corpora.

Lucee 2,115 to 1,991, no finding added.
- **`import "com.x.Class";` brings in a Java class, and the import reaches every function body.** The quoted form was not read, so `new GreenMail()` was a component called GreenMail that does not exist; it is a value of unknown shape now. A function body parsed later (every one `FuncRefs` asks for) was parsed without the file's imports at all, so an imported name was right in the first parse and wrong in the second. A local that aliases such a name (`var mail = application.testSMTP`) is as dynamic as the name. Lucee 1,991 to 1,942, ColdBox 13 and Masa 11 fewer through the alias rule.

TestBox's HTML reporters set `variables.helper` and render every partial through an include: 108 findings (524 to 416), and 12 in Masa. No finding is added on any of the seven workspaces.
- **`copy = duplicate( orig )` is typed as `orig` is.** A copy of a component is an instance of the same component. Lucee's duplicate tests were 76 "no component ref" (2,191 to 2,115). A pair where a function is written onto either name (`orig.injected = function(){}`, which the copy carries) is not typed, and neither is a copy of something untyped or a literal. No finding is added on any of the seven workspaces.
- **A computed `#…#` after the FROM clause of a literal HQL query no longer hides the entity.** `ormExecuteQuery( "FROM Payment WHERE #column# = :id" )` is evaluated before it is sent, so the rows are still Payments; the entity is read from the text before the first hash, which must end in a space (so `FROM Loaded#x#` and `FROM #x#` are still untyped). 8 findings in Galaxie Blog (272 to 264).
- **An include through the application's root variable reaches its template.** `<cfinclude template="#application.baseUrl#/common/function/page.cfm">` was skipped (a path with a hash is not read), so a template could not see the functions its includer's other includes declare: 67 bare calls in Galaxie Blog (`getPageMode`, `getTemplatePathByPageName`) were "no qualifier, not in file" and 7 receivers an include hands on were untyped (346 to 272). Only a plain variable whose last name segment says it holds a root (`baseUrl`, `basePath`, `appRoot`, `webRoot`, `rootDir`) and a slash after it counts; `#dynamicDir#/page.cfm` is still not read. No finding is added on any of the six workspaces.

Galaxie Blog's `Setup.getOwner()` returns `entityLoadByPK( "Users", id )` or a null cast, and its 27 callers' `owner.getEmail()` were "no component ref" (375 to 346); one finding goes in FW/1's qBall. No finding is added on any of the six workspaces.
- **A function that returns one element of an entity array returns the entity.** `var found = ormExecuteQuery( "FROM ShopOrder WHERE …", { … } ); if ( arrayLen( found ) ) { return found[ 1 ]; }` was an untyped `any`, so `var o = loadOrder( id ); o.getCurrency()` was "no component ref". Every return of the function must be such a read, of collections whose elements are one component (a bare `return;` does not count against it). 100 findings in Galaxie Blog (475 to 375); no other workspace changes.
- **`<cfset x = createObject( "java", … ).init()>` is the Java object.** The tag parser asked about the last call of the expression, `init`, so the form without `.init()` and the script form were typed and this one was not. `var html = createObject( "java", "java.lang.StringBuilder" ).init()` then `html.append( … )` was "no component ref": 89 findings in Galaxie Blog (564 to 475) and 6 each in TestBox and ColdBox.
- **An argument passed a loop variable or an element of a collection is typed by the collection.** `for ( var row in entityLoad("X") ) { save( row ); }` and `save( found[ 1 ] )` passed what the collection holds to the caller index, which typed only plain variables, so the callee's `arguments.thing.m()` was "no component ref". Galaxie Blog's `Bookings.toStruct( entity )` accounted for 54 findings (618 to 564); ContentBox loses 5 and no workspace gains one.
- **A `<cfset>` whose value starts on a later line is no longer recorded twice.** `<cfset var m =` then `array(…)` on the next line recorded the call on the tag's line as well as its own, because the value was trimmed before its line was counted. Lucee's `menu.cfm` and `ext.providers.cfm` were the two files it showed in, against the tree-sitter grammar.
- **`unresolved` no longer reports SQL as unresolved calls.** SQL in a triple-backtick island (`query ds {``` … ```}` or a `<cfquery>` in one) and the body of a `java { … }` block were read as script, so `VARCHAR(255)`, `sum(x)` and a Java method signature were recorded as calls: 16 findings over Lucee's tests ("`to_char` not found in extends chain"). A call written in a `#…#` inside that SQL is still a call.
- **A call in a property default or a component attribute is found** (`property name="u" default="#createUUID()#"`, `component hint="#now()#"`), as is one in a script that follows a string holding `</cfscript>`, and `for( property in x )` is a loop over a variable and not a property declaration.
- **A call written over several lines in a `#...#` span is found when its string holds an apostrophe or an escaped hash.** `#ETH.text( "<p>Don't</p>… ##f2dede …" )#` was split at its first `<`, which lost that call and the one after it. ContentBox's email templates are written this way; seven files across ColdBox, ContentBox and Lucee gain calls, and one new `unresolved` finding appears in ContentBox, for a call the parser had been missing.
- **Calls on a variable named `default`, and in a hash expression that holds another one, are found.** `default.get( "Test" )` was read as the `switch` keyword and its receiver dropped; `#event.buildLink( a & #encodeForHTMLAttribute( id )# )#` was closed at the inner hash, in the middle of the call, which lost both calls. Neither adds an `unresolved` finding over ColdBox, TestBox, FW/1 or ContentBox.
- **A call in a chain written a call per line is reported on the line its name is on**, not the line the chain began on: the calls after `command( … )`, a scope's first call (`variables.print` then `.line()`), a receiver alone on its line, the hops after `createObject( … )` or `new X()`, and a call after a `]`. Findings in `unresolved` and `explain` move to the line the call is written on, and two ColdBox findings disappear that were caused by the old line (a call put before the assignment that types its variable). A committed known-issues report shows line-number churn the next time it is regenerated.

### Added

- **A shared-scope variable is typed from the templates that set the request up.** `REQUEST.context.getUser()`, in a file that never assigns `REQUEST.context`, used to need a `componentResolvers` entry matching the name. The server now reads the `SCOPE.name = value` assignments in the templates the governing `Application.cfc` includes, transitively, and in the new `startupFiles` config key, which applies to every file, including those under no `Application.cfc`. A `startupFiles` entry may be a template path such as `/tassweb/packages/tass/core/bootstrap.cfm`, resolved like a `cfinclude`. It is tried after every assignment the calling file, its `Application.cfc` and its extends chain make, and the answer is still method-checked. In tassweb, with the full config, the unresolved calls are identical. Without the `context` resolver, 6,013 shared-scope calls depended on it. The automatic lookup leaves 692, the calls under no `Application.cfc`, and `startupFiles` leaves none. Six public projects give identical results.

- **A workspace folder implies a mapping of its own name.** With `../tassweb` in `workspacePaths`, the dot-path `tassweb.packages.tass.core.kernel2` resolves to `<tassweb>/packages/tass/core/kernel2.cfc` with no `mappings` entry. The same holds for a `cfinclude` template and for go-to-definition on a path such as `/tassweb/includes/header.cfm`. It is tried last, after every configured mapping, every `Application.cfc` mapping and every lookup relative to the file, the application and each workspace folder, so nothing that resolved before resolves differently. `mappings` are read as before and still needed for any root that is not a folder's name. tassweb's three mappings (`tassweb`, `tassreporting`, `tassdoc`) each named a workspace folder by its own name. Without them 250,708 of its calls stopped resolving; with this change, removing them changes no call. Six public projects give the same unresolved calls as before.
- **Crash reports always go to a file.** `crash.log` in the server's cache directory, `~/Library/Caches/cfmleditor-lsp/crash.log` on macOS, holds a record of every crash, with nothing to configure. With `CFMLEDITOR_LSP_LOG` set, they go to that file instead. Each start adds one line naming the version, the process and the time, so a record below it can be tied to a run; anything else in the file is a crash record. Three kinds reach it:
  - the Go runtime's own crash report (`debug.SetCrashOutput`), for the crashes nothing in the server can catch: a panic in a goroutine with no `recover`, and fatal errors such as a fault in tree-sitter's C code, a concurrent map write, a stack overflow or running out of memory. Until now each left only a traceback on stderr, which belongs to the editor and is lost when it stops reading;
  - the panic that ends the server, recorded as it goes;
  - every panic the server recovers from and keeps running after.

  For a fatal error the one-line reason (`fatal error: stack overflow`) still goes to stderr only; the file gets the traceback, which names the fault in its frames.
- **A recovered panic's log record carries its stack.** The eight places that recover a panic and keep going, among them the request handler, background jobs, both edit timers, workspace indexing and three parser entry points, logged the panic's value alone, such as `index out of range [3] with length 3`, which names no function. Each record now has a `stack` field, and the parser's three are errors rather than warnings.

### Changed

- **Completion sends less when the editor can fetch the rest.** A client that lists `documentation` and `detail` in its `resolveSupport` (VS Code and Neovim do) is sent the built-in and member-function items without them, and `completionItem/resolve` fills them in for the item it highlights. The response shrinks from 322KB to 144KB and takes 40% less time to build and encode. A client that does not list them is sent the full items, as before.

### Fixed

- **Typing outside a function no longer reparses the file on every keystroke.** An edit at component level (a property, a comment above a function, the component's attributes) made the server reparse every function signature in the file before it read the next message: 95ms per keystroke in a 65,000-line component. The reparse now waits until something needs the result, and the next request pays for it once. Keystrokes there cost under 3ms.
- **`cfmleditor.goToMatchingTag` and known-issues underlines counted columns in bytes.** On a line with an `é` or an emoji before the tag, go-to-matching-tag found no tag or jumped to the wrong column. A known-issues entry's underline landed after the method it names, and a whole-line one ran past the end of the line. Both now use UTF-16 units. CFLint's own columns were already right, since CFLint counts UTF-16 units.
- **An absolute path in `workspacePaths` is used as written.** Every entry was joined onto the config's directory, so `/srv/shared-lib` became `<config dir>/srv/shared-lib`, a folder that does not exist: the server indexed nothing from it, a `workspaceIndexGlobs` entry naming it matched no files, and `cfmleditor-lsp unresolved .` reported "Indexing 0 files". A relative entry is still taken from the config's directory, as `mappings` and `beanPaths` always were.

## [0.3.8]

### Fixed

- **A slow request no longer holds up every message behind it.** The server handled one message at a time, each to completion, so formatting a 65,000-line component (1.5s) delayed every hover, highlight and keystroke sent meanwhile. Formatting, range formatting, `cfmleditor.explainCall`, `cfmleditor.exportDeps` and `cfmleditor.findRefs` now take the document's text and do their work alongside later messages.
- **Formatting answers with the lines it changed, not the whole document.** The response was one edit replacing the file, which the editor then diffed against the buffer itself; on a 65,000-line file that was 3.6MB. It is now the changed runs of lines. A reindented line still counts as that line, so an untouched line between two changed ones stays out of the edits, and on an already formatted file only what changed is sent.
- **The explain code action no longer parses the file on every cursor move.** Deciding whether to offer "Explain call resolution on line N" parsed the whole document after each edit, which on a 65,000-line component cost 87ms each time the cursor settled. It now reads the cursor's line. The command still parses, so its answer is exact.
- **`cfmleditor.exportDeps` drew a thinner graph after an edit outside a function.** It read the document's cached parse result, which an edit outside a function reparses shallowly, dropping every call site inside one. The graph then fell back to the component refs the index holds, so it showed `controller.cfc --> service.cfc` where it had shown each function called and the functions those call, until the next edit inside a function. The file-level graph that the "Export dependency graph for <file>" code action draws was affected the same way. It now parses the text the editor holds, as `cfmleditor.explainCall` does.
- **A large batch of edits held a document for most of a second.** Reverting a reformat in Zed sends one `didChange` holding an edit for every line the formatter changed, and the server applied them one at a time, each walking from the top of the document and copying it. 6,000 edits against a 110 KB file took 435ms, and every request on that file waited behind it. A batch in document order is now applied in one pass, in about 5ms. It is the server's share of the pause after reverting a format; if the editor itself stops responding, that is the editor's work, not the server's.

Both calls are now recorded from the receiver and walked through their return types, and the variable is typed by that walk rather than by the resolver's guess at the text. An indexed receiver keeps its `[]`, so `phrase[1].font()` is no longer read as a call on `phrase`.

- **A bare call to a function held in the variables scope was reported missing.** `#VARIABLES._render()#` in a string in a tag file is recorded as a bare call, and CFML looks a bare name up in the variables scope, so a call to a name the file assigns there (`VARIABLES._render = ARGUMENTS.render`) is now accepted as a call through that property, as the qualified form already was.

- **Most calls in tag files had no caller.** A call found in a `<cfif>`, `<cfset>` or `#...#` expression is recorded by a sub-parser that never knew the function it was in, and a region cut from a function body (after a `<cfscript>` island or a `<script>` block) names no caller either, since its `<cffunction>` tag was in an earlier region. Across the TASS workspace that was 514,852 of 895,451 calls. Every call is now given the function whose lines hold it, which is what find-references shows as the calling function and what a call through `ARGUMENTS.fn()` is resolved against.

- **Markup between two stray hashes was read as CFML.** A tag file's text was scanned for every `#...#` pair, and ColdFusion evaluates one only in an output context, so `href="#"`, CSS colours, jQuery `$('#id')` and Handlebars `{{#each}}` paired up and every `name(` between them became a call. Text is now scanned only inside `<cfoutput>`, `<cfquery>`, `<cfmail>` and `output="true"` functions, the rules measured against Adobe ColdFusion, while the attributes of CF, `cf_` and cfimport-prefixed custom tags are scanned wherever they stand. A `.cfm` with no CF tags that holds HTML is read as markup rather than CFScript. The same stray hashes also hid real tags from the tag walk, whose `<cfif>` conditions are now found. `features.outputContextInterpolation` switches it off. Across the TASS workspace: 45,180 unresolved entries to 44,622, none added; 782 calls no longer extracted, every one outside an output context, and 496 found that were not.

- **A variable assigned through a chain was typed by its first call.** `chart = b.width(1).height(2).build()` took the type of `width`, the builder, so every method of the chart it holds was reported missing from the builder; `x = createObject(...).builder().build()` took the created class. The calls after the first are now kept on the ref and walked by their declared return types once the parse is done, in script and in `<cfset>`. `init()` counts as returning its object, and a call that declares no type makes the variable dynamic rather than leaving it the earlier type. A lookup made during the parse no longer reads such a ref before it is walked.

- **A call chained after `createObject(...)` or `new` was checked against the created class.** In `createObject("java", "FirebaseOptions").builder().setCredentials(c)`, `setCredentials` was looked up on `FirebaseOptions`; each hop now carries the hops before it, so it is looked up on what `builder()` returns. An untyped `init()` in a call chain keeps the object too.

- **A chain through a dynamic value stopped being dynamic.** Once a hop returned `$any`, as `getSandBox("x")` does, the walk asked `$any` for the next method and reported it missing: `getSandBox("x").getAttendanceObj().getLog()` was "method 'getAttendanceObj' not found in $any". The rest of the chain is now accepted as dynamic, as a call directly on `$any` already was. 157 entries on tassweb.

- **A component that names no file is reported as missing, not as lacking the method.** It is nearly always a componentResolver producing a path that does not exist, such as a broad `get$1()` catch-all turning `getInjectorController()` into `tass.injectorcontroller`, so "component 'X' does not exist" now points at the config rather than at code. On tassweb, 192 entries changed from one reason to the other, 62 of them java stubs that were never generated.

- **A chain rooted at a bare call offered the resolvers only its first string argument.** `createObject("java", "java.net.URLEncoder").encode(s)` was offered as `createObject("java")`, which the java-stub pattern cannot match, so `encode` was reported as a bare call. The leading run of string arguments is now offered, as the assignment path already did.

- **A call chained off a resolved factory call lost the component its argument named.** In `getService("company").getList()` the resolver matched `getService("company")`, then the next hop was recorded as a chain off the bare name, and chain entries carry no arguments. Resolving it again saw `getService()`, which only a broad `get$1()` catch-all could answer, with the wrong component; a chain rooted at a bare call was reported as "no qualifier, not in file". The hop now starts from the component the first call resolved to, on every path that reaches it: an assignment, a statement, a scoped receiver, a struct-member target, a condition, a nested argument, a named argument (`getService(service="x")`) and no argument at all (`getObjInit().getMailServer()`). The bare-call path also called `tryResolveCall` after its arguments had been consumed, which never matched and consumed the `.` that followed, losing later assignments in the same block. On tassweb, `unresolved` drops from 28,137 to 3,547.

### Added

- **A bare call resolves through cfinclude.** An included template runs in its includer's variables scope, so a template mixed into a component can call what the component declares, what it extends and what any sibling template declares, and a page can call what it includes. These were all "no qualifier, not in file"; they now resolve, and go-to-definition and the call graph follow them. On tassweb this is 814 of the unresolved entries, with none added.

## [0.3.2]

### Added

- **Go-to-definition now answers variables.** `<cfargument>`, `var`/`local.`/`variables.`/`this.` assignments, `<cfparam name>`, `<cfloop index>`, and the `url`/`form`/`cgi`/`cookie`/`client`/`application`/`request`/`session`/`server` scopes, written scoped or bare. An unscoped name follows CFML's own search order — local and arguments before variables, variables before the request scopes — so a bare `total` inside a function with `var total` resolves to its own rather than to a `url.total` on the page. A declaration inside the enclosing function outranks one outside it, and among several the nearest at or before the cursor wins, which is the rule component refs already followed.

  The four shared scopes resolve **across files**, because that is the point of them: `application.x` is written in `Application.cfc` and read everywhere, `server.x` in `Server.cfc`. Only those four ever read another file, and only when the current one does not declare the name, so an ordinary lookup stays local.

- **Script parsing allocates 74% fewer objects and is 15% faster** (2,087 allocations per parse down to 543). The scanner allocated a one-byte string for every operator, brace, paren, comma and semicolon in the file — 42% of every object a parse allocated, from a single `string(ch)`; it reads a table now. The dotted-chain builders allocated a buffer for every `x = y` in the file whether or not anything was ever appended to the first identifier, which is what most chains are.

- **Tag parsing is 2.9x faster and allocates 47% less** (222µs to 76µs on the benchmark component, 110KiB to 58KiB, 27% fewer allocations), from changes three profiles pointed at. `getAttr` lowercased the whole tag on every call, and a `<cffunction>` is asked for five or six attributes. `indexCFTag` — the search the entire tag scanner is built on — walked byte at a time calling `EqualFold` at every `<`, when a page is full of angle brackets and almost none of them start the tag being looked for. `buildLineIdx` made two byte-at-a-time passes over the whole source per parsed file. All now go through the stdlib's vectorised scanners, and each rewrite is checked against the implementation it replaced over generated input rather than a few chosen cases.

  A second profile, taken once scanning was no longer the bottleneck, showed allocation was: `ParseVars` classified the file and then called `FindFuncScopes`, which classified it again, building a second line index over the whole source every time; and every `<cffunction>` allocated a map to record the locals it declared, whether or not it declared any. Both are gone.

  A third, once those had landed, found `extractSignatures` calling `findTagFuncScopes` over the whole file **twice**, under two guards testing the same condition — 18% of everything a tag parse allocated, spent scanning the file again for an answer already in hand. Beside it, the check for whether a scope was already recorded scanned every scope per candidate, which is quadratic in a component's method count. And the set of function-local variable names was a map of lowercased keys, paying for buckets and a `strings.ToLower` on every insert and every lookup, to hold the handful of names a function declares.

  The line index was the last of them, and it was built three times per parse — once by `ClassifyRegions`, once for the whole file's function scopes, once per region parser — over what is, for a single-region file, the same string. `ClassifyRegions` hands back the one it built, and the offsets are `int32`: one entry per line of every file parsed, where a file big enough to overflow one is 2GB of source.

### Fixed

- **Go-to-definition answered nothing when a component called its own method through an unresolvable receiver.** A qualified call whose receiver the parser cannot type — `VARIABLES._svc.doThing()`, an `any` argument, a chain, a bracket index — falls back to looking the method name up in the index. That fallback discarded any definition in the requesting file, so where the name was declared only there, the answer was nothing at all while the name sat in the index the whole time. The definition is now kept and ranked **last**: the qualifier is evidence against it (`x.doThing()` is not a call to this component's `doThing()`), and nearest-first would otherwise rank it top, since nothing is nearer than the same file — `myObj.init()` would land on the caller's own `init()` ahead of every real candidate.

- **The server's own log lines reached the editor as failures.** Everything it logged went to stderr, and `vscode-languageclient` reports a server's stderr at error level whatever it says — so the startup banner, "indexing complete" and a genuine fault were indistinguishable in the Output panel, all three prefixed `[error]`. The server now also sends `window/logMessage`, which carries a severity the client can render honestly. Both, not one instead of the other: stderr is the only place a record can go before the client connects or after it disappears, and a crash during startup is exactly when the reason matters most.

### Added

- **The extension's own go-to-definition suite now runs against this server** (`internal/server/definition_conformance_test.go`). Same cases, same cursor-marker syntax, fixtures copied from the extension with their source commit recorded. It exists because the extension stands its own providers down whenever this server runs, so every case it answers and this server does not is something a user loses by enabling the server — and nothing could say which those were.

  **All 41 pass.** They did not at first: 16 were one gap, with no variable branch at all. `knownGaps` is empty now and deliberately kept, because the test **fails when a known gap starts passing** — that is what made closing them a ratchet rather than a claim.

### Added

- **`cfmleditor.resolveRoute`** — answers "where does this route go" for a route the caller supplies, rather than one found in a document. It exists so an editor command that takes a route by hand and go-to-definition on a route in source resolve through the same code: an editor keeping its own copy of the convention was the state of things before, and two resolvers reading two different configs disagree quietly — the one that is wrong still opens a file, just not the right one. Returns every target with its URI, component, method and declaration range, so a caller can reveal the method rather than the top of a ten-thousand-line controller.

  A workspace with no `routes` block gets an answer, not an error: a JSON-RPC error is not something an editor command handler can put in front of someone, so the reason comes back in the result.

### Fixed

- **Only a function's first argument was read for a route.** A route is as often passed by name — `setRequestContext(route="a.b.c")`, `setRequestContext(r="a.b.c")` — or one call down in `redirect(buildRoute("a.b.c"))`, and none of those were found. ### Added

- **Two views that do not render the whole map**, because at 54,000 nodes none of the others can. **Drill-down** starts at the top-level directories and expands one level at a time, so what is on screen is a function of what you opened rather than how big the map is — the first frame of a 54,000-node map is a dozen circles. **Focus** draws one node and everything within *n* hops, on a ring per hop, and clicking any node re-centres. Neither is capped, because neither was ever going to draw more than you asked for.

  The hierarchy is derived from the paths already on each node rather than stored: the path already *is* the hierarchy, so a second representation could only disagree with the first. Groups aggregate their members' edges, and a group counts as utility only if all of it is — the same rule `Collapse` uses.

Both take an optional options object (`level`, `format`, `out`, `under`, `from`, `live`, `detached`, `open`) and both work invoked with no arguments, so an editor can bind either to a menu item. Entry globs, utility globs and `hideUtility` come from the `codemap` config block exactly as they do for the CLI.

  The build reuses the server's own index rather than making one. That index is already current — `didChange` and the watched-file handler maintain it — so the generate skips the index pass, the more expensive half of a cold CLI run. It runs on its own goroutine and reports through `window/showMessage`, because a map of a large workspace takes seconds and a blocking `executeCommand` freezes the editor. Output is confined to the workspace: a command an editor invokes with arbitrary arguments is one that can be asked to write anywhere.

Tagged, not removed — marking has never been a filter.

### Fixed

### Added

They describe the codebase rather than one invocation, so every person and every tool that builds the map describes the same one — a map built without them reports different dead code and a different set of hubs, and nothing about the result says which run was configured correctly. The command-line flags add to the config rather than replacing it.

Marked, never excluded: it is genuinely the most-depended-on code in a workspace (on one, the entire top ten by fan-in), so removing it would misreport what depends on what, while leaving it unmarked makes every ranking a list of it. ### Fixed

The viewer also offered no filter for them. `TestEveryEdgeKindIsEncodable` now checks every kind round-trips and that the viewer offers a filter for each.

### Added

- **Framework routes (`routes` in `.cfmleditor.json`)** — convention-based routing is invisible to static analysis. A dispatcher reads a dotted route out of a URL or an HTML attribute, builds a component path and a method name from it and invokes them; nothing in the source names either, so every routed controller method looks uncalled and every view unreferenced. On one real workspace, teaching the LSP the convention revealed **542 controller methods reached only by a route** — every one of them a false positive in the unreferenced list before.

  `suffixes` strips a trailing segment that says how a target is presented rather than what it is — `kiosk.lms.lms_grades.iframe` is the route `kiosk.lms.lms_grades` loaded inside an iframe container. The route is tried as written first, and suffixes are stripped before aliases are applied so an alias need not be written once per presentation.

  Routes are written four ways and all are scanned: HTML attributes, `?do=` URL parameters (unquoted, so they end at a delimiter rather than a quote), JavaScript object keys quoted or bare, and function arguments such as `redirect("a.b.c&x=1")`, whose value is cut at the first delimiter rather than rejected for carrying one.

  The convention is configuration, not code. `${N}` is one segment, `${N+}` everything from N on, `${N-M}` a span; `:concat` joins without the dots, `:slash` with slashes, `:lower`/`:upper` fold case; `:search` enumerates method start points longest-first, because a route does not say where the controller's name stops and the method's begins — the same shape is `studentMainStudent()` on one controller and `mainStudent()` on another. Controller rules are tried in order and the method has to exist, which is what makes the order safe — a component template built from the first segment matches enormous numbers of routes and would otherwise shadow every rule below it. An alias may name several replacements, for a route segment that means "whichever product is serving this page": all of them resolve, the code map marks the edge as a guess, and go-to-definition offers the choice. A view path template controls its own separators — a literal `/` between directories, and whatever join the segment reference asks for inside a name — so `"webroot/${2}/${3+}"` finds `webroot/assessment/dialog.objectivegroup.setup.cfm`. Views take either a path template or `longestDir`, which finds the longest leading run of segments naming a real directory and treats the rest as a dotted file name — a split no template can express, because it depends on what is on disk.

  FW/1 and TASS are both expressible, and `TestFw1Convention` resolves FW/1 through the same machinery to keep the grammar from quietly becoming one framework's rules.

- **`cfmleditor-lsp routes`** — reports every framework route found in a workspace and what it resolves to. `--format md --out routes.md` writes a report worth keeping: it groups the unresolved ones by *shape* (how many carry a `dialog` segment, a `popup`, an action verb), because a whole row is usually one missing rule rather than one problem per route, and it separates prefixes that resolve on other routes — where the controller is found and only the method name is underivable — from prefixes that resolve nowhere, which is a different fix. Every route is cited with file and line. `--format json` for scripts, plain text for the terminal.

- **Routes in the editor** — go-to-definition on a route string jumps to the controller method's declaration or the view file, and every unambiguously-resolvable route in a document gets a link. Ambiguous routes are left to go-to-definition, where the editor can present the choice, rather than a link silently picking one of several products.

- **Route edges in the code map**, distinct from calls because they are a convention resolving rather than a call site parsing. The build reports how many routes it found and resolved: a low share means the config describes a different convention from the one in use, and the route edges are worth correspondingly less.

- **`cfmleditor-lsp graph` — a whole-project code map.** Every function and file, and the calls, instantiations, inheritance and includes between them, in one streaming pass. On an 11,769-file workspace that is 60,439 nodes and 105,622 edges in about ten seconds. Four levels (`function`, the default hybrid of functions *and* files; `call`, the strict call graph; `file`; `package`) and six formats (`text`, `json`, `jsonl`, `dot`, `mermaid`, `html`).

  **Every declared function is in the map whether or not anything calls it.** Unreachable code is not dropped and not folded into the main graph: it becomes its own island with its own root, which `--detached` lists and the HTML report draws as a separate tree. A map that quietly omitted what it could not connect would describe a tidier codebase than the one on disk.

  Calls from top-level `.cfm` code are attributed to the file node, and that is the larger half of the graph rather than an edge case — 74,226 of 107,683 call sites on a real workspace. An implementation recording only calls inside function bodies would lose a page-heavy application almost entirely.

- **`--format html` — a self-contained interactive report.** Four views, because no single picture works at every size: hierarchical edge bundling grouped by island then directory; a force layout giving each island its own centre, so detached code sits apart instead of being pressed against the border; a dependency matrix, which has no occlusion at any size; and an islands view of the disconnected pieces. Above ~1,200 nodes the force view renders to a canvas with a quadtree for hit-testing, so it stays interactive into the tens of thousands.

  The page embeds its JavaScript — a 76KB D3 bundle of only the modules these views use, built from `internal/codemap/assets/vendor` by `make update-d3` and committed. No CDN and no network: a report opens the same on an air-gapped machine, and still renders years later.

- **`--db <file>` — SQLite persistence and an incremental cache.** The map is stored with indexes and an FTS5 trigram symbol index, so `sqlite3` is a supported way to query it. The per-file parse cache is keyed on each file's content hash *and* a fingerprint of every indexed component and config, because resolving a call reads the index built from every other `.cfc`: keying on content alone would serve a stale edge set after an unrelated file moved a method. Roughly 15 seconds cold against 7 warm.

- **`cfmleditor-lsp mcp` — the map over the Model Context Protocol**, read-only by construction. `search_symbols`, `get_symbol`, `get_callers`, `get_callees`, `find_path`, `list_islands`, `list_orphans`, `get_stats`, and `explain_call`, which re-parses a file and traces how a call site's receiver was typed and which `componentResolver` fired.

- **`resolve.ResolveCallTarget`** — runs exactly the resolution `CanResolveCall` runs and also reports where the call landed. `canResolveCall` already found the callee and threw it away. Rather than widen its return across twenty-odd `return ""` sites, each accept path records alongside its existing trace step, and `TestEveryAcceptPathRecordsATarget` parses the source and fails on an accept path that forgets.

- **`--entry <glob>`** marks files as entry points by path, for code a runner invokes by a constructed name — release scripts, scheduled tasks, plugin directories. No static analysis can see `createObject("component", "prs" & version)`, so those files look unreferenced and are not: on one workspace a single release-script directory was 10,639 of 11,374 apparently-unreferenced functions. A bare directory name matches everything beneath it; private methods are never marked.

### Fixed

- **`collectCFMLFiles` skipped a hand-kept list of directories**, not every dot-directory, so `.claude/worktrees` — git worktrees holding a complete second copy of the codebase — was scanned as though it were source. On one workspace that doubled every count and added thousands of phantom entries. `unresolved` and `scan` are affected as well as `graph`.

### Notes for multi-application workspaces

- **Each file is resolved under its own `.cfmleditor.json`.** A workspace is often several applications side by side, each with its own config and each listing the others in `workspacePaths`, so any scan reads all of them. Under a single config the other applications' `componentResolvers` never fire — which does not error, it simply resolves nothing and leaves those files with no edges. `--one-config` restores the old behaviour.

- **`--under <path>` keeps the nodes just outside the prefix that an edge crosses into**, marked as boundary nodes. Cutting hard at the prefix removes every caller from elsewhere, which is exactly what you scoped the map down to find: on one package that was 472 edges against 7,999. `--under-strict` does the hard cut.

It stays inside the open buffer — nothing is parsed and no file is read — which is why it is on by default where "find all references" is opt-in.
- **`textDocument/foldingRange`**, opt-in with `{"features": {"folding": true}}` — folding on CFML structure instead of the editor's indentation guess, which gets tags wrong constantly (`<cfelse>` sits at the same indent as its `<cfif>`). Ranges come from the syntax tree, and every one stops short of its closing line so `</cfif>` and `}` stay on screen. A script-syntax `.cfc` folds properly too: its body is one opaque region to the outer grammar, so each injected region is parsed and walked in its own right. It is off by default because it is the most expensive request the server answers: that same opaque region means folding a script component parses its whole body afresh each time. Left off, the editor folds by indentation as before.
- **`textDocument/rangeFormatting`** — the editor's "Format Selection", which previously did nothing at all. The whole document is formatted and only the edits inside the selected lines are returned, so a selection can never be formatted differently from the same lines under format-on-save. A change that straddles the edge of the selection — the formatter joining a five-line `<cfif …>` header onto one line, say — is left alone rather than half-applied: nothing outside the selection ever changes.
- **The index now tracks files changed outside the editor.** The server asks the client to watch the workspace for `.cfc`/`.cfm` changes (`workspace/didChangeWatchedFiles`) and re-indexes, or drops, each one. Nothing to configure and no extension change: it is a server-initiated registration, so any client that supports dynamic registration starts watching on its own. Clients that don't are told in the log that the index will not track disk changes.
- The editor's **`insertFinalNewline` and `trimFinalNewlines`** (LSP 3.15) are now honoured. VS Code defaults both to `false`, and the formatter was adding a final newline and trimming trailing blank lines regardless. `trimTrailingWhitespace` stays unhonoured — output is rebuilt from the syntax tree, so there is no trailing whitespace to preserve.

### Fixed — formatter

- `formatting.lowercaseTags: false` did nothing. `<CFOUTPUT>` still came back `<cfoutput>`, and `<CFDUMP>` came back as `cfDUMP`. Opening and closing tags now each keep the casing they were written with.
- A `//` comment among a function's parameters **deleted the parameter after it** — `a, // why, b` lost `b` into the comment. Same defect for a comment among a function's annotations, and among a function *expression*'s parameters.
- An `import` statement before `component` switched off `//` comment recognition for the whole file, so the safety guard compared comment text as though it were code. Same cause as the UTF-8 BOM fix — a token before `component` the probe did not step over. Five of the 5,624 corpus files are affected; it only became a visible refusal under `commaPosition: "before"`, but the guard ran weakened on all five in every mode.
- `queryExecute(…)` calls were never formatted — arguments unindented, and `parenSpacing`, `commaPosition` and `indentWidth` never reaching them. The grammar gives this one call a node of its own, which the formatter had no renderer for, so it was emitted verbatim. 137 of the 5,624 corpus files contain one. The SQL itself is still emitted exactly as written: it is a string literal, so re-indenting it would change what the query says.
- A braced `case` body (`case 1: { … }`) put its brace in column one and folded the switch's closing brace onto the block's (`}}`).
- A trailing comma was silently deleted from every list — `[1, 2, ]`, `{ a: 1, }`, `f(1, 2, )`. The form is legal in Lucee, ACF and BoxLang.
- A `.cfm` whose body is JavaScript (Lucee's `jquery.blockUI.js.cfm`) had its `//` comments folded, commenting out the code after them. The only case where the formatter silently destroyed a file.
- `</cfcomponent>` with no opening tag crashed the formatter, so the file could not be formatted at all. Reachable by deleting a component's opening line.
- Several `whitespaceOnly` guard defects that made the formatter refuse correct output — so format-on-save silently did nothing. Causes: a `/*` inside a string literal, a backslash read as an escape (CFML escapes quotes by doubling), an interpolation holding its own strings, a lone `#` in a `<script>` region, a UTF-8 BOM, and classic Mac line endings.
- `<cfset x = /* why */ f()>` lost the comment; `cfparam (name:"x")` had its colons rewritten to `=`; an array declaration with a trailing `// note` gained a stray comma.

## [0.2.8]

- Fix every file URI the server hands a client being built as `"file://" + path`, which is a valid URI only for a POSIX path containing no character that needs escaping (#45). A Windows client was sent `file://C:\Users\q\Application.cfc` - two slashes instead of three, backslashes, and a bare drive colon - and could not open it; the canonical form is `file:///c%3A/Users/q/Application.cfc`. On macOS and Linux the same concatenation left a space unescaped. This affected `window/showDocument` from `cfmleditor.openActiveApplicationFile`, every `Location` returned by go-to-definition for a component or `<cfinclude>` path, and `DocumentLink` targets.
- Fix the same boundary in the inbound direction, which is why the Windows report could not be a one-line change. The server recovered a path from a document URI with `strings.TrimPrefix(u, "file://")`, which leaves percent-escapes in place: given a spec-compliant `file:///tmp/uri%20demo/src/index.cfm`, `cfmleditor.openActiveApplicationFile` looked for `Application.cfc` in a directory that does not exist and answered "No Application.cfc found". Every Windows URI fails the same way, yielding `/c%3A/Users/...`. Conversion now goes through `cfpath.FromURI`, which decodes properly but keeps the trim as a fallback for the raw `file://C:\...` form some clients send, since that parses as a URI whose authority is the whole path and whose path is empty, so asking it for a filesystem path returns nothing at all.
- Fix `resolve.EnsureIndexed` and the extends-chain and `Application.cfc` ref lookups keying the index by the hand-built form. On Windows those keys could never match the entries the workspace scan writes through `uri.File`, so `this`-scope completions, inherited method resolution and `Application.cfc` component refs found nothing; and because `EnsureIndexed` also writes, the malformed URI reached the client as a go-to-definition target. On POSIX both forms already normalised to one key through `uriKey`, so that part changes nothing there.

- Fix `refs` always reporting `"filesScanned": 0`. The field was declared on `RefResult` and never assigned, so every response said the search had covered no files at all - including responses carrying references, which made a successful scan read like a failed one, and made a genuine miss indistinguishable from a search that never ran. `refs.FindCalls`/`FindComponentRefs` return the size of the walked file set alongside the entries now, through a shared `FindCounted`; `Find` keeps its single-value signature for its existing callers. The count is the number of CFML files the walk turned up, not the number parsed, since `findInFiles` deliberately skips parsing any file whose text cannot contain the target and that smaller number would describe an implementation detail rather than the search.

- Fix every `--mermaid` diagram failing to render. `nodeID` sanitised a node label into an identifier by replacing five characters (`.` `/` `:` space `-`) and leaving everything else, but Mermaid reads several of the rest as shape delimiters. Since every dependency node label carries a `(line N)` suffix, `deps --mermaid` emitted `UserService_cfc_(line_0)["UserService.cfc #40;line 0#41;"]`, where the identifier ends at the `(`, `(line_0)` is read as a rounded-node body, and the `["..."]` that follows is a syntax error. The label had been escaped all along; only the identifier had not. Identifiers now keep `[A-Za-z0-9_]` and replace everything else, so `refs --mermaid`, `deps --mermaid` and `cfmleditor.exportDeps` all produce a diagram that parses.
- Fix `refs` reporting "no references found" when given no name to search for. An editor with no symbol under the cursor sends an empty target, and `refs "" <dir>` scanned nothing and exited 0 with `{"target": "", "filesScanned": 0, "refs": null}` - indistinguishable from a genuine miss. It now says so and exits 1.

- Fix `format` ignoring every `formatting` key in `.cfmleditor.json`. The subcommand built its options from `formatter.DefaultOptions()` alone and never looked for a config, so `format -w` and the editor's own format produced different bytes for the same file whenever the workspace set `indentWidth`, `lineWidth`, `attrBreakThreshold`, `commaPosition`, `scopeCase`, `lowercaseTags` or any of the other fourteen knobs the LSP handler applies - it was the only subcommand that skipped config discovery, while `deps`, `explain`, `refs` and `unresolved` all do it. Config is now discovered from each file's own directory upwards, with `--root <dir>` to name one explicitly (same semantics as `explain --root`), and both entry points map config onto formatter options through one shared `config.ResolvedFormatting.FormatterOptions()` rather than each restating the field list. `UseTabs` remains the one setting with no config key: the LSP derives it from the editor's `insertSpaces` and the CLI keeps the `formatter.DefaultOptions()` value.
- Fix `format -w` writing files the LSP refuses to format. `textDocument/formatting` bails when tree-sitter reports an ERROR or MISSING node, because formatting an incomplete CST is how a grammar gap becomes deleted source, but the CLI had no such check and went straight to `formatter.Format` - leaving only the `whitespaceOnly` guard, which `.ai/docs/FORMATTER-ISSUES.md` records as blind to comment-joining, between a grammar gap and the user's file. Both paths gate on one shared `formatter.ParseError` now, so a file the editor declines is a file the CLI declines, with the same message.
- Fix `format -w` clobbering permissions, bumping mtimes needlessly and truncating in place. The write was a bare `os.WriteFile(path, out, 0o644)`: a `0600` or `0755` file silently became `0644`, an already-formatted file was rewritten regardless (bumping its mtime, which is enough to wake every file watcher and rebuild on the tree) and reported as `formatted`, and a failure partway through left a half-written source file with no copy of the original anywhere. Unchanged output is no longer written at all; otherwise the replacement goes through a sibling temp file that is fsynced, chmodded back to the mode of the file it replaces, and renamed over the target - following a symlink to its target rather than replacing the link with a regular file. The rename also re-checks that the file on disk still matches what was read, so output computed from stale bytes cannot silently overwrite an edit that landed while the formatter ran.

The body is an `expression_statement` rather than a `statement_block`, and the block renderer walks named children only, so the `;` — an anonymous child — was never emitted. The grammar's `variable_declaration` accepts `var`, `final`, or the combined `final var`/`var final` as its leading keyword, each its own anonymous child, but the renderer's keyword-detection loop only recognised `var`, so it walked past `final` every time and fell back to its `"var"` default. The same loop was duplicated for a `for (...)` clause's inline declaration and had the identical bug; both now go through one shared `declKeyword` helper. Caught by the `whitespaceOnly` guard, so in practice format-on-save silently did nothing to the file. 2 files in the formatter corpus.

Caught by the `whitespaceOnly` guard, so in practice format-on-save silently did nothing to the file. 3 files in the formatter corpus.

The grammar wraps `?.` in a named `optional_chain` node, the same way it wraps `::` in a named `static_chain` node — `memberOperator` special-cased the latter but not the former, so its fallback loop, which only inspects *anonymous* children, never found the operator and fell through to the default `"."`. The `whitespaceOnly` guard caught it — `?` is not whitespace — and refused to write the result, so in practice this was the `new component {}` failure mode: format-on-save silently did nothing to the file rather than corrupting it. 4 files in the formatter corpus.

The `whitespaceOnly` guard cannot catch it — only whitespace changed — but the attribute's value did change, and for a CFML tag whose attribute carries a string the runtime uses, a `cfhttpparam` value or a `cfmail` subject, the injected whitespace is in the data. - Fix `componentResolvers` being tried in a different order by different features. `ResolveFromCallMatch`, behind `CanResolveCall`, walks the configured slice in order; `ResolverSet.Resolve`, behind completion and hover, collected candidates by walking the *call site's* bytes, so resolvers were tried in order of where each `prefix`'s first byte happened to appear in the text. Where two prefixes share a first byte the bucket was already in array order, which is why the documented `getDirectContent()`-before-`get$1()` case kept working; where they differ, the same expression resolved to two different components depending on which feature asked, and the documented way to override a broad catch-all worked in one half of the LSP only. Sorting the candidates back into configuration order also collapses the duplicates a pipe-delimited `prefix` contributed, which makes the path about twice as fast rather than slower.
- Finish characterising the grammar refusals in `.ai/docs/FORMATTER-ISSUES.md`: thirteen more `tree-sitter-cfml` gaps reduced to minimal repros and re-verified standalone against a control that parses (subscripted `::` static access, `${ }` ordered-struct literals, `exit "x";`, `savecontent` as an expression, a `new` expression as a tag-in-script attribute value, colon-separated and mixed-separator tag-call attribute lists, brace-less `try`, a dot-notation numeric struct key on assignment — which parses when read — the `call():function(){}` listener form, a return type written before the access modifiers, `pageencoding` before a component, and `name: value;` colon assignment). About a third of the candidates turned out to parse on their own and are recorded so they are not re-filed. Also corrects two earlier claims: the ColdBox refusals were recorded as malformed source for omitting a comma between parameters, but that form parses in CFML and the gap is already filed, and the reducer handles all 83 refusals rather than 81.
- Make `ShiftLines` cost the edited file rather than the whole index. It runs on every line-count-changing keystroke and holds the index write lock while it does, so in daemon mode its cost is paid by every other session's lookups — and it was scanning every bucket of the function and ref maps to find one file's entries, then rebuilding all five maps wholesale. On a 5,000-file workspace that was 18ms per keystroke; it is now 6µs where method names differ between files. What remains proportional to workspace size is the by-name buckets: a workspace where every component defines `init` has one bucket holding an entry per file, and replacing this file's entries still rebuilds that slice — writing in place is not available, since callers hold the slice after the read lock is released. That worst case improves 20x rather than going flat.
- Fix hover and definition answering with the component a variable held *before* an edit. Two causes, both defeating a fix made earlier in the same cycle. `reparseShallow` cleared only the `funcVars` cache and left `funcRefsMap`, `funcCallsMap` and `funcLinksMap` holding pre-edit results — `ApplyFullReplace` runs through it, and so does the rapid-change path after any large paste, so `FuncRefs` served a stale answer that the server then faithfully re-indexed; deleting a function's last `new Foo()` left its ref in place for the same reason, and `FuncCalls`/`FuncLinks` went stale alongside, affecting the dependency graph and in-function document links. Separately, the per-function ref entries were keyed by the function's *line range*, which moves the moment a line is inserted above it, so each re-indexing wrote a new entry instead of replacing the old one and the stale entry won the closest-preceding-line tie-break. All four caches are cleared together now, and the key is the function's name, which survives editing.
- Trace function-level dependency graphs past the first hop. `cfmleditor.exportDeps` scoped to a function produced one level and stopped: `getFuncCalls` returned nothing unconditionally, because the index it consulted stores function definitions and component refs but never call sites, so there was nothing to continue from — no `MaxDepth` made a difference, and the test that claimed to cover "transitive deps through service to persist" passed throughout because its assertions were substring matches on an edge label that an unresolved edge also satisfies. `deps.Options` gains a `LoadCalls` hook returning a function's calls together with the refs that resolve their receivers; the refs travel with the calls rather than being read from the index because a receiver may be a function-local `var x = new Foo()`, which is not a file-level `ComponentRef` and never reaches the index. The server implements it by parsing the target on demand, memoised for the life of one command. File-level graphs were always transitive and are unaffected; leaving the hook nil keeps the old behaviour, so the `deps` CLI is unchanged. A cycle test pins that two components calling each other terminates now that the traversal genuinely recurses.
- Fix tag-based functions being indexed under the wrong name. `getAttr` looked for an attribute name as a plain substring and only checked the text *after* the match, so a hit inside a longer attribute counted: `name` matched the tail of `displayname=`, and `<cffunction displayname="Donor Lookup" name="getDonor">` was indexed as a function called `Donor Lookup` — with its `<cfargument displayname="Donor Id" name="donorId">` indexed as `Donor Id`. - Fix the formatter changing non-whitespace content. Audited by formatting 5620 CFML files from Lucee, ContentBox, ColdBox, FW/1, TestBox and cfmleditor: 1671 were rejected by the `whitespaceOnly` guard, so with the default settings the LSP silently declined to format them and format-on-save did nothing. 5450 now format cleanly and 84 are still rejected.   - CF tags that are legal without a body — `cfmodule`, `cfhttp`, `cfinvoke`, `cffeed`, `cfadmin` — were given a closing tag they never had, which re-parented every following sibling into the tag's body.

## [0.1.11]

### Added

- `queryFormat` config option to control whether `<cfquery>` content is formatted (default `false`).
- `queryCommaPosition` config option with `"preserve"` (default), `"before"`, and `"after"` modes.
- Preserve mode for SQL comma placement — keeps commas in their original position by default.
- Adjacency-aware formatting — nodes without whitespace in source (e.g. `table#var#_suffix`, `<cfif>name_a<cfelse>name_b</cfif>`) stay glued together.
- Goto-definition support for component resolvers, includes, and dot-path references.
- Release tooling (`make release <version>`, `make release-dry <version>`).

### Changed

- Renamed SQL formatter options to use `query` prefix: `queryFormat`, `queryUppercaseKeywords`, `queryCommaPosition`.
- `queryCommaPosition` defaults to `"preserve"` independent of `commaPosition`.
- `queryFormat` defaults to `false` (query content emitted verbatim unless opted in).
- `make build` now runs `update-grammar` (regenerates tree-sitter grammar + clears Go cache).
- Release workflow embeds version from git tag into binary.

### Fixed

- Stale Go build cache not picking up tree-sitter grammar changes (added `go clean -cache` to `update-grammar`).
- Commas inside `<cfif>` blocks no longer incorrectly repositioned in trailing-comma mode.
